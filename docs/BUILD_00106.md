# BUILD-00106 — per-operator reviewer identity binding

**Date:** 2026-11-16  
**Branch:** `build-00106-reviewer-identity-binding`  
**Base:** `integration/build-00086-00096-final`

## Change

- Added `backend/reviewer_auth.py` to resolve a submitted review token to a configured reviewer ID.
- Preferred configuration is `NEXUS_REVIEW_CREDENTIALS_JSON`, a JSON object mapping reviewer IDs to unique random tokens (32–512 ASCII characters).
- When individual credentials are configured, the legacy shared `NEXUS_REVIEW_TOKEN` is ignored.
- Legacy-only deployments remain compatible, but every legacy request is recorded under the fixed identity `legacy-operator`; client-supplied reviewer IDs cannot spoof another operator.
- Review approval, rejection and policy-evidence audit events now use the authenticated reviewer ID instead of trusting the request body.
- Invalid credentials return 401. Malformed credential configuration returns 503 and never falls back to the legacy shared token.
- Updated `.env.example`, backend README and operator runbook with rollout instructions.

## Validation

Automated tests cover individual identity resolution, invalid and duplicate credentials, weak tokens, legacy migration behavior, fail-closed configuration and audit identity spoofing attempts. CI result pending.

## Security boundary

This is per-operator token authentication and audit identity binding, not a full external identity-provider integration, session management or role-based authorization system. Tokens remain bearer credentials. Use HTTPS, distribute each token securely, rotate compromised tokens, and add an IdP/RBAC layer before broad multi-user or public deployment. No live deployment or production credential was used.
