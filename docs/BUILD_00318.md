# BUILD-00318 — Safe recovery for orphaned review-pending development jobs

**Status:** Implemented; hosted CI passed on PR merge commit.  
**Branch:** `build/build-00318-orphaned-review-pending-recovery`  
**Parent:** BUILD-00317 exact Draft PR review-artifact completion gate  
**Scope:** Development-control plane only. This does not change customer content publishing.

## Problem

BUILD-00317 correctly leaves a development job in `review_pending` if the stable automation Draft PR cannot be verified. That prevents false completion, but it leaves an operator recovery gap when the PR action succeeded earlier and the workflow stopped before persisting the exact review artifact.

## Implemented recovery behavior

- Added paginated, read-only retrieval of all open pull requests for the configured repository.
- Added `recover_pending_reviews`, which searches only for the stable automation head branch and expected default base branch.
- A candidate must be an open, unmerged Draft PR whose head and base repositories both equal the configured repository and whose head contains a full commit SHA.
- Recovery requires exactly one candidate. Zero candidates or multiple candidates leave every job and immutable event unchanged.
- A unique candidate is re-read by exact PR URL; the existing publisher verifies repository identity, Draft/open state, exact head SHA, expected branches, and every changed file before recording completion.
- Added `backend/recover_development_reviews.py`, a bounded command that performs recovery only. It never invokes Aider/Ollama and never creates, updates, approves, merges, closes, or deploys a PR.
- Added a manual workflow-dispatch choice: `develop` runs the normal approved development cycle; `recover` skips model setup, code generation, and PR creation and performs read-only evidence recovery only.
- Recovery exits non-zero when pending or ambiguous work remains, so the workflow does not report a false green result.

## Safety boundaries

- No automatic requeue when no PR is found. The existing diff may be present in a runner worktree or an unpublished branch; resetting the job could duplicate or discard work.
- No deletion, rewrite, reset, or mutation of existing branches, PRs, job rows, or audit events.
- An operator must inspect the stable automation branch/worktree and decide how to handle a no-match case. Explicit requeue with preserved history is intentionally not part of this change.
- Customer-facing public publishing remains behind the existing human approval workflow.

## Tests added

- Unique existing Draft PR is recovered and exact PR/file verification is repeated.
- No matching PR leaves job status and event history unchanged.
- Multiple matching PRs are treated as ambiguous and leave the job unchanged.
- No pending jobs causes no GitHub API request.
- Workflow contract asserts that recovery is manual, read-only, and skips model execution and PR creation.
